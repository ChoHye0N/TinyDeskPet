# ADR-0003: OS 기본 창 드래그 대신 직접 드래그 구현

| 항목 | 내용 |
|---|---|
| 상태 | 승인 |
| 날짜 | 2026-10-01 |
| 관련 요구사항 | FR-10, FR-12, FR-16, NFR-PERF-04 |

## 맥락

프로토타입은 `WM_NCHITTEST`에서 `HTCAPTION`을 반환해 OS가 창을 끌게 했습니다. 이 방식은 간단하지만, 사용자가 창을 끄는 동안 Windows가 **자체 모달 메시지 루프**(`DefWindowProc` 내부)를 돌리기 때문에 우리 메인 루프가 멈춥니다. 그 결과

- 드래그 중 애니메이션(숨쉬기, 흔들림)이 멈추고,
- 캐릭터가 "끌려가는 중"이라는 사실을 로직이 알 수 없으며,
- 놓는 순간의 속도(던지기, FR-16)를 계산할 수 없습니다.

## 고려한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| A. `HTCAPTION` 유지 | 코드 없음 | 위의 문제 |
| B. `HTCAPTION` + `WM_TIMER`/`WM_MOVING`에서 렌더링 | 모달 루프 중에도 그리기 가능 | 렌더링 경로가 두 개가 되고 타이머 정밀도가 낮음 |
| **C. `SetCapture` + `WM_MOUSEMOVE`로 직접 이동** | 메인 루프가 계속 돎, 드래그 상태가 도메인 로직에 있음 | 구현 코드가 조금 늘어남 |

## 결정

**C**를 선택합니다. 플랫폼은 마우스 입력을 **화면 좌표 이벤트**로만 전달하고, 드래그 판정과 위치 계산은 `CharacterController`가 합니다. `Application`은 매 프레임 캐릭터 위치에 맞춰 창을 옮깁니다.

이벤트의 화면 좌표는 `GetMessagePos()`로 얻습니다. 창이 움직이는 중에 클라이언트 좌표를 `ClientToScreen`으로 바꾸면 메시지 발생 시점과 처리 시점의 창 위치 차이 때문에 떨림이 생기기 때문입니다.

## 결과

- 좋아지는 점: 드래그 로직을 단위 테스트할 수 있습니다. 던지기, 화면 경계 처리 등을 도메인에서 확장할 수 있습니다.
- 감수하는 점: 창 이동이 우리 루프의 프레임 속도에 묶입니다 (VSync 60Hz면 충분).
- 후속 작업: M1에서 드래그 속도 추적(최근 N개 샘플의 평균)으로 던지기를 구현합니다.
